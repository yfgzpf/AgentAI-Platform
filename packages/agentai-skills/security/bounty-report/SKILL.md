# Bounty Report — 把漏洞变成"能过审拿钱"的报告

挖到洞只是开始，**报告写得过不过审 = 钱能不能到手**。这个技能把 `.agentai/vulns/vulns.jsonl` 里落盘的漏洞，整理成各平台认的格式。

## 触发条件

- 用户说"提交漏洞 / 出报告 / 写赏金报告 / 报洞 / 这些洞怎么提交"
- pentest-workflow 跑完落了几条 `report_vulnerability`，下一步要出报告

## 第一步：定级 (CVSS 简化版，平台认这个)

按 4 维给严重度，直接决定赏金档位：

| 维度 | 判据 | 示例 |
|------|------|------|
| **影响范围** | 只影响自己 / 影响他人 / 影响全量用户 / 影响后端数据 | 全量用户 > 他人 > 自己 |
| **可利用性** | 一条 PoC 直接打 / 要前置条件 / 要多步链 | 直接打 > 要前置 |
| **危害类型** | 数据泄露/提权/支付/账号接管 > 信息泄露 > DoS | 危害越重越高 |
| **是否越权** | 普通用户能干到管理功能 = 高 | 水平/垂直越权单独加分 |

**严重度 → 赏金档**（各平台不同，这是量级参考）：
- **Critical**：远程 RCE / 全量数据泄露 / 支付篡改 / 提权到 root → 赏金最高档
- **High**：可复现的 SQL 注入 / 账号接管 / 垂直越权 / 可写 shell → 高
- **Medium**：XSS（能弹其他用户/带 cookie）/ CSRF 改关键操作 / 敏感信息泄露 → 中
- **Low**：反射型 XSS 只弹自己 / 信息泄露（无敏感数据）/ 缺失安全头 → 低

⚠️ **定级宁低勿高**：平台审核会按实际危害定级，吹高了反而被降档 + 拉黑。一个 High 写虚成 Critical，过审时被打回比真 High 拿的还少。

## 第二步：复现证据规范 (过审的关键)

平台 90% 的打回是"复现不了 / 证据不足"。每条漏洞必须备齐：

1. **可一键复现的 PoC** — 复制粘贴就能打（curl 命令 / 浏览器 console 脚本 / 请求报文三选一，给全最好）
2. **前后对比** — 正常响应 vs 注入后响应（diff 片段，证明真生效）
3. **截图/录屏** — 弹框/越权操作/数据泄露的画面（赏金里"眼见为实"）
4. **影响面说明** — 这条洞能影响到谁、最坏能干什么
5. **修复建议** — 给个能落地的修法（平台认"你懂怎么修"，加分）

**没复现的洞不要报**：半确定的猜测报上去 = 浪费 + 被标记"低质量提交者"。`report_vulnerability` 落盘时已经要求"复现成功且有证据才存"，出报告时只挑落盘的。

## 第二步·补：影响证明自检 (为什么同样的洞别人过审你被打回)

平台 triage 每天看几百条报告，**"这里有个洞"不值钱，"这个洞能造成多大损失"才值钱**。同样是 IDOR，写"可以越权访问"和写"用账号 B 能读到账号 A 的订单收件人手机号，涉及全量用户" —— 前者 Low，后者 High。

**四问自检，缺一条就回去补证据（不许编）：**
1. **谁能被影响** — 只有我自己 / 特定条件的他人 / 全量登录用户 / 未登录匿名也能打
2. **前置条件** — 需要登录？需要特定角色？需要诱导受害者点链接？条件越少定级越高
3. **最坏后果** — 读到什么级别的数据 / 能改谁的数据 / 能不能接管账号 / 影响多少资金
4. **证据到哪一步** — 只证明"响应有差异" / 拿到了真实数据样本 / 完整复现了危害链

**补证据的安全做法（与 pentest-workflow 同源）：**
- 越权：两个**自己的**测试账号交叉验证（A 的资源 ID 给 B），不遍历真实用户
- 数据泄露：只取 **1-3 条**样本，姓名/手机号/证件号**脱敏**（如 `138****1234`）后再贴进报告
- 文件读取：用 `/etc/hostname` / `win.ini` 这类无敏感内容的文件证明，不读 `.env` / `application.yml` / 私钥
- SSRF：证明能到达内网/元数据地址即可（状态码/长度差异），不获取任何云凭证
- 支付：只在自己创建的测试订单上验证，不产生资金流，不动他人订单
- 后台未授权：只做只读 GET 探测，不改配置、不爆破

⚠️ **补证据 ≠ 加大破坏**。批量拖真实数据、真实接管他人账号、使用泄露凭证 —— 这条报告会因为**取证方式违规**被直接拒收甚至封号，比不报更糟。报告里始终保留"最小强度、无破坏"声明。

## 第三步：平台选择 + 提交清单

| 平台 | 适合 | 提交前要做的 |
|------|------|-------------|
| **HackerOne** | 海外/大厂，赏金高 | 先查该项目的 scope 页，**确认资产在 in-scope**；提交走 triage |
| **补天** | 国内，门槛低 | 注册+实名认证；选对目标方；注意有些要"先报备" |
| **漏洞盒子** | 国内，响应快 | 同上；重复提交会被合并给先报的人 |
| **各厂 SRC** (阿里/腾讯/百度/字节) | 自家资产 | 走官方 SRC 入口；有些要求走先知平台 |
| **CNVD/CNNVD** | 想拿证书/排名 | 偏合规漏洞，赏金低但认 |

**提交前 checklist（每条洞过一遍）：**
- [ ] 在目标方的授权范围内（out-of-scope 资产 = 封号/法律风险，**别报**）
- [ ] 没和该目标已公开/CVE 重复（先搜 CVE + 平台已归档列表）
- [ ] 复现 PoC 能独立跑通（找个人照做一遍）
- [ ] 定级实事求是（宁 Low 实，勿 Critical 虚）
- [ ] 截图/证据齐 + 给了修复建议
- [ ] 没顺手碰生产 / 没破坏数据（报告里声明"已做最小强度验证，无破坏性操作"）

## 第四步：批量出报告

用 `read_file` 读 `.agentai/vulns/vulns.jsonl`（一行一条 JSONL），逐条套上面模板。可一次出多条，但**按严重度排序**（Critical → Low），让平台 triage 一眼看到最值得修的。

## 报告模板 (单条，适配各平台)

```
## 漏洞标题
[严重度] [类型] - [影响资产] - [一句话描述]
示例: [High] SQL注入 - 用户查询接口 - 未过滤导致可读取任意表

## 漏洞概要
<目标功能> 处存在 <类型>，攻击者可 <危害>。

## 复现步骤
1. 前置: <需要什么样的账号/路径>
2. 操作: <构造的 payload>
   ```
   curl "https://目标/api/search?q=' UNION SELECT username FROM users --"
   ```
3. 观察: <正常响应 vs 注入后响应对比>

## 影响/危害
- 影响范围: <自己/他人/全量>
- 最坏后果: <数据泄露/提权/支付/账号接管>
- 定级理由: <为什么是这个严重度>

## 修复建议
<输入参数化/过滤 + 最小权限 + WAF 规则，给具体代码或配置>

## 验证证据
- 截图: <路径或图>
- 关键响应片段: ```
  <响应体>
```
- 声明: 仅做最小强度验证，未执行破坏性操作，未碰生产数据。
```

## 红线 (与 pentest-workflow 同源)

- 只报授权范围内的洞；out-of-scope 资产**一个字别提**
- 不夸大定级、不报没复现的洞
- 报告里明确"最小强度、无破坏" —— 这是你和"真攻击者"的界限，也是平台认你的前提
- 提交前再 `list_scope` 确认目标还在授权内（授权过期就别提交）
